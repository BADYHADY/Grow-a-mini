============================================================
0. THE MOST IMPORTANT THING — THE VISION
============================================================

THIS IS THE NORTH STAR OF THE ENTIRE PROJECT.

The game is heavily inspired by the successful Roblox game:

GROW A CHICKEN FIGHTER

We are NOT copying their IP, assets, code, UI or characters.

We ARE deliberately taking inspiration from the proven STRUCTURE and gameplay loop that makes that type of game work.

The key twist is much stronger and more personal:

INSTEAD OF GROWING A CHICKEN,
THE PLAYER GROWS A MINIATURE VERSION OF THEIR OWN ROBLOX AVATAR.

The player's real Roblox avatar becomes their little fighter.

The marketing/product sentence is:

"BRO, LOOK WHAT MY AVATAR TURNED INTO."

That sentence should be used as a filter for major design decisions.

Another shorthand:

GROW YOURSELF.
TRAIN.
FIGHT.
MUTATE.
FUSE.
ASCEND.
BECOME RIDICULOUS.

The fantasy is NOT:

"I collected a rare pet."

The fantasy is:

"LOOK WHAT I TURNED MY ROBLOX AVATAR INTO."

This player-identity angle is our primary differentiator and potential viral moat.

============================================================
1. WHAT THE GAME SHOULD FEEL LIKE
============================================================

This is extremely important.

The game should be closer to:

Grow a Chicken Fighter
+
tycoon/simulator progression
+
collection/build optimization
+
social flexing

NOT:

a mechanically intensive action game where the player manually controls every attack.

Most gameplay should be SEMI-AUTOMATIC or AUTOMATIC.

The PLAYER:

- chooses what their Mini should do
- chooses training stations
- chooses upgrades
- chooses builds
- chooses mutations
- chooses fusion combinations
- chooses which fights/challenges to enter
- optimizes progression
- collects Forms
- watches progression
- makes strategic choices

The MINI:

- trains automatically
- fights automatically
- performs attacks automatically
- grows automatically from progression
- uses its animations automatically
- performs activities once commanded

The player is essentially the coach/owner/builder of their own miniature fighter.

Think:

PLAYER CHOOSES ACTIVITY
        ↓
MINI DOES ACTIVITY
        ↓
REWARD
        ↓
UPGRADE / MUTATE / FUSE / PROGRESS
        ↓
WATCH MINI BECOME MORE RIDICULOUS
        ↓
REPEAT

We specifically discussed that it should feel somewhat like a tycoon in how much of the repeated activity is automated.

DO NOT drift into:

"click every punch"
"manual WASD fighting as the Mini"
"four combat abilities constantly controlled by the player"
"complex Souls-like combat"

That is NOT the core game.

19. CURRENT WORKING MINI APPEARANCE
============================================================

Current Mini appearance has been tested visually.

Originally hair disappeared.

Root issue discovered:

The old filter assumed:

IsLayered == body clothing

which is false because important identity accessories such as Hair/Hat/Face can also appear as layered accessories.

We changed the logic to preserve identity accessories.

Result:

hair returned.

The user said the Mini looked perfect and approved moving forward.

Current product rule:

IDENTITY > PREMATURE OPTIMIZATION.

Do not remove the player's hair/accessories/clothing simply to save a few parts unless performance data proves it necessary.

20. CURRENT AVATAR ARCHITECTURE
============================================================

Current preferred implementation:

- fetch player's HumanoidDescription server-side
- build a real R15 model
- preserve player identity
- use Roblox model scaling rather than inventing a custom incompatible skeleton
- Mini is roughly small/collectible-sized
- normal player pose is mirrored to Mini

Earlier R6 RigScaler code may still exist in repository history or source.

R6 was Candidate A and was technically elegant, but R15 won because:

- better modern avatar compatibility
- better identity retention
- layered clothing support
- same topology as normal player
- pose mirroring
- more natural animations

Do NOT revert to R6 without strong evidence.

24. REMOTE / SECURITY PHILOSOPHY
============================================================

The existing Remotes architecture had good ideas and should generally be preserved.

Client-to-server traffic is INTENT only.

Server decides:

- currencies
- damage
- rewards
- rarity
- items
- mutations
- purchases
- inventory
- Power
- Tower rewards
- Ascension rewards

Client owns:

- presentation
- camera
- VFX
- UI
- visual interpolation
- local animation presentation

Every ClientToServer Remote should:

- be declared
- have rate limiting
- validate payloads server-side

The client should NEVER say:

"I dealt 500 damage."

It says something like:

"I requested attack X."

Server verifies and decides.

25. DATA ARCHITECTURE
============================================================

DataService uses ProfileStore.

Goals:

- session locking
- schema versioning
- migration table
- Studio mock data by default
- safe player-leave handling
- future offline progression

During testing Studio Output reports:

[ProfileStore]: Roblox API services unavailable - data will not be saved

This is expected while running mock/Studio without live API access.

DO NOT mistake it for gameplay failure.

We found one important migration issue previously:

Reconcile() must NOT erase knowledge of an old schema version before migrations know what version data was on.

A patch was written to migrate before reconcile / safely handle old profiles.

Verify the current DataService retains the safe ordering.
